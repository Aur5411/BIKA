## 新增与改动

**章节目录**

- 修复 100 话以上只加载出二三十话：并发翻页 + 整体超时 + 5 分钟缓存 + 不轻信服务端空页
- 服务端截断时按章节序号补出缺失的前置章节（占位标题形如「第 12 話」），可直接点开阅读
- 边拉边显示：第一个网络来回就铺出前 20 话，不再整屏转圈；失败仍整份报错，不展示残缺列表
- 新增按钮：回到顶部 / 回到底部 / 正序倒序（连同原下载共四个，同尺寸同配色），
  两个滚动按钮同一组显隐、动画不互相打断
- 顶部信息行写明状态：「共 160 话 · 最新话在前」，加载中显示「已加载 20 话 …」

**首页** 移除顶部「最近浏览漫画」（设置页未动）。

**分流 / 网络** 冷启动自动探测并切到最低延迟线路（API 与图片成对选取）；设置页测完延迟
自动应用最低延迟 IP；IP 分流增强（多 IP 边缘池、并发探测、失效黑名单、按 `/24` 归并、快照兜底）。

**图片加载** 补上缺失的图片磁盘缓存（Coil 不会自动创建），此前每次冷启动都要重下所有封面。
现在内存缓存 25%，磁盘缓存按可用空间 2% 自适应（64 MB ～ 2 GB）。

**图片加载速度**（本轮）

- **最快源自动选路**：竞速决出的最快域名会被记住，之后的每张图在进 Coil 链之前就
  改写到它，不再"每张图都先打一遍慢源"。源失效即忘掉重选，选路结果 10 分钟后过期重测
- **补请求头**：图片链路原来没有浏览器 UA / Referer，Cloudflare 前面的镜像
  （实测 `storage.tipatipa.xyz`）会对默认 OkHttp UA 直接 403；403 会被降级逻辑当成
  "主源失败"，于是每张图都要白跑一轮换域名竞速
- **竞速阈值 2.5s → 0.9s**：慢源不再被白等两秒半才去找更快的源
- **并发拉满**：图片同域名并发 16 → 32、全局 64 → 128，连接池与解码线程池跟着配齐；
  Coil 的取流/解码改用专用线程池，不再和下载、数据库抢同一个 `Dispatchers.IO`
- **预载拉大**：预载并发 5 → 12（原来小于窗口宽度，窗口根本喂不满），
  快读窗口 10 → 16、精读 3 → 6，基准预载默认 2 → 8，设置滑杆上限 16 → 24
- **候选源** 全部候选统一由 `ImageHosts` 维护（`img.picacomic.com` 曾在池中，
  后经实测确认其在 `/static/` 下恒 404，已于 v1.11.33 移除）

**图片加载速度**（第二轮：找根因）

第一轮把并发、预载都拉满了，但实测发现并发数换不来带宽——根因不在参数，在协议：

- **强制图片链路走 HTTP/1.1**：图片 CDN 支持 HTTP/2，OkHttp 默认优先 h2，于是所有图片
  被塞进**同一条 TCP 连接**多路复用，而这个 CDN 上的 h2 吞吐只有几十 KB/s。同一份文件、
  同样并发数实测：h2 单连接 44 ~ 115 KB/s，HTTP/1.1 多连接 1784 ~ 3007 KB/s，
  **差 20～60 倍**。h2 下再大的 `maxRequestsPerHost` 也换不成吞吐，必须钉死协议，
  上面那 32 并发才有意义
- **连接预热**：一次 TLS 握手实测 1.0～1.3 秒，连接复用时首字节才 400ms——"第一张图迟迟
  不出来"里有一大截是在做密钥协商。进入阅读会话时并发摊好几条连接放进池子里 idle 5 分钟
- **提前选路**：预热阶段顺带并发探一遍所有候选源，把最快的那个先记下来，第一张图就直接打它，
  不必再从慢主源起步、熬到竞速阈值才去找更快的源
- **可见页按画布采样解码**：`AsyncImagePainter` 在没设 `sizeResolver` 时会兜底成
  `SizeResolver.ORIGINAL`，2000×3000 的扫描页也被解成同尺寸 Bitmap（单张 20 MB 起），
  解码时间随像素线性增长。现在按画布约束采样，只砍掉超出屏幕的冗余像素

同一轮的验证过程里也排除了两条路：CDN 支持 Range，但**多线程分片拉一张图反而更慢**
（8 线程只有单线程的 0.89 倍，还偶发失败），所以没有走这条路；多条连接，h2 下不存在这个前提。

**读一会儿之后图片全部加载不出来**（第三轮：修限流)

图片跑快之后出现的新问题：长章节翻过二十来页，后面的图再也出不来。原因是服务端
对短时间内的图片请求做配额限制，超限回 429，而降级逻辑把 4xx **一律**当成"这个 path 上
就是没有"的永久性失败——于是每张图直接判死，既不换源也不重试，同时预载还在满并发继续拽图，
把配额烧得更干净。修法是把"被限流"当成一等公民处理：

- **429 / 503 不再判死**：交给外层 `ImageThrottleInterceptor` 等窗口过去再重试同一张图
- **全局节流闸门**（`ImageRateGovernor`）：在飞请求上限 16；吃到限流就指数退避
  （1.2s → 2.4s … 上限 30s），一次成功即清零自愈
- **限流期间不再打 source 竞速**：配额通常按 IP/账号计，此刻并发打其余候选域名只会更快烧光
- **预载在限流期直接放弃**：用户此刻看不见它，它的边际收益是负的，让出配额给可见页
- 传输层超时/5xx 的可见页请求补一次退避重试；预载不重试，避免为"下一页更快"多付请求量
- 取流/解码的并行闸门改用 `Dispatchers.IO.limitedParallelism`：原先的自建固定线程池下，
  竞速子协程与等待中的父协程排在同一批线程上，有线程饥饿风险

**榜单** 加 10 分钟缓存，从漫画返回榜单不再重新转圈。

**阅读器** 上下章改由「章节序号 + 服务端自报总数」判定，目录被截断或尚未加载完时
「下一章」不再被误置灰；首章无上一章、末章无下一章。

**其它** 修复下载完成后进度不置 100；修复阅读进度防抖写入会把进度写退；详情页标签改惰性列表；
补齐多个模块缺失的测试依赖，430 项单元测试全部通过。

### v1.11.34 修复说明：查明 `tobs/` 是后端选择段，补上唯一能兜底的源

这一版是顺着"为什么**换源也救不回**某几页"往下挖出来的，结论比前几轮更靠底层。

**发现的机制**：路径里的 `tobs/` 不是普通目录，而是**后端选择段**——
它的含义是"这份文件在 storage-b 后端"。实测（路径 `sub_storage_1/7f/8b/<真实 uuid>.jpg`）：

| 域名 | `/static/tobs/sub_storage_1/…` | `/static/sub_storage_1/…`（无 `tobs/`） |
|---|---|---|
| `storage.diwodiwo.xyz` | 301 → `storage-b.diwodiwo.xyz/static/sub_storage_1/…` → **200** | **404** |
| `storage.tipatipa.xyz` | 301 → 同上 → **200** | **404** |
| `storage-b.diwodiwo.xyz` | 301（自我剥掉 `tobs/`）→ **200** | **200** |

**这为什么致命**：换源逻辑**只改 host、保留 path**。如果服务端给的 `path`
恰好不带 `tobs/` 前缀，那么换到池子里**任何一个**"路由器"域名，拿到的都是 404；
遍历一圈全灭 → 被判定成"服务端缺图" → 界面报 **"图片不存在（HTTP 404）"**，
而那张图其实完好地躺在源站上。这就是"某几页怎么重试都出不来"
**只发生在 100 页以上长篇**的成因：长篇的页会落进 `sub_storage*` 分桶目录，
分桶目录才需要 `tobs/` 做后端路由；短篇的页直接是 `/static/<uuid>.jpg`，不涉及。

**修复**：把 `storage-b.diwodiwo.xyz` 加进候选池并**排首位**。
它是 storage-b 后端本身，实测对 8 种路径形态（有/无 `tobs/` × 3 个真实 uuid
+ 1 个普通图）**全部 200**，是池子里唯一能接住"path 不带 `tobs/`"的节点；
串行兜底的顺序即尝试次序，所以必须排第一，放队尾等于白放。
同时它省掉一次跨域 `301`，`DEFAULT_HOST` 也一并换成它。

`ImageHostsTest` 新增一条用例把这个顺序钉死：能兜住无 `tobs/` 路径的节点
必须在首位。

### v1.11.33 修复说明：把"现场"直接印在失败卡片上 + 路径形态自愈

**先把上一轮没验证到的一环补上了。** 用户第三次报告时贴回的地址里，那个"空格"
我一直只能靠肉眼判断。这次把它**原样写到磁盘再按字节读**，得到确切码位：

```
目录段 = 'sub_storage 1'
码位   = ... U+0073 U+0074 U+006F U+0072 U+0061 U+0067 U+0065 U+0020 U+0031
                                          ↑ 就是这个：U+0020 SPACE（Zs 类别）
```

**它就是一个 U+0020 普通空格**，不是什么 NBSP、零宽字符之类的隐藏字符。

这带来一个**确定的推论**：`page.url` 是 `Media.safeImageUrl` 的结果，而
**从 v1.11.30 起就会把 U+0020 替换成下划线**。所以一条带空格的 URL
**在 v1.11.30 之后的版本里不可能被打印出来**——看到它就说明装的不是这一版。

所以这一版做了两件事：

**1. 失败卡片上直接印出"现场"，让截图自带全部证据**

```
图片不存在（HTTP 404）
点击重试
—
第 7 页  ·  v1.11.33          ← 一眼确认装的是哪一版
host: storage-b.picacomic.com
url: https://.../static/tobs/sub_storage_1/7f/8b/....jpg   ← 归一化后的（请求用的）
原始 path: tobs/sub_storage 1/7f/8b/....jpg                ← 服务端原样给的
可疑字符: [11]U+0020(SPACE)                                ← 不可见字符及其码位
```

- `url` 是**归一化之后**、真正发出去的地址，永远看起来是干净的；
- `原始 path` + `可疑字符` 是**服务端原样给的**数据与码位清单。

这两行放在一起，才能区分"是我们拼错"还是"服务端数据脏"——而这正是过去
三轮报告里缺失的那一块。只有真的存在可疑字符时才多占这两行，正常路径不显示。

**2. 路径形态自愈：归一化失败就退回服务端原样路径**

"把不可见字符换成下划线"是**基于实测的强假设**（`sub_storage%201` 在多个源上
全部 403、`sub_storage_1` 全部 200），但它终究是假设——没人能保证源站永远只有
下划线这一种拼法。

所以现在不留退化成"赌一种拼法"：先按归一化后的地址请求，**只有它返回 403/404 时**，
才用服务端原样给的路径再试一次。服务端日后无论改成哪种拼法，应用都能自己走出来，
不必再发一版。

开销可控：正常情况（归一化后成功）**一次请求都不多**；只有已经失败的图才各多一次，
且外层降级换源对每次请求都有整体预算，UI 侧重试另有退避，不会指数放大。

**3. 顺手把 `ChapterPage` 带上服务端原始 `path`**

归一化会把"数据本来是什么样"抹掉，导致报错时无从对照。原始值随页面一起带下去，
只用于失败时自证，不参与任何请求构造。

**4. 清掉候选池里两个"根本不是图片节点"的域名（这条才是 404 的来源之一）**

为了确认"空格到底是不是脏数据"，做了一次全矩阵实测（8 个域名 × 6 个边缘节点，
同一张图、两种拼法）：

| 域名 | `sub_storage%201`（空格） | `sub_storage_1`（下划线） |
|---|---|---|
| `storage-b` / `storage1` / `s3` / `s2` | 403 ×6 | **200 ×6** |
| `storage.diwodiwo.xyz` / `storage.tipatipa.xyz` | 403 ×6 | **200 ×6** |
| `img.picacomic.com` | **404 ×6** | **404 ×6** |
| `www.picacomic.com` | **404 ×6** | **404 ×6** |

结论有两层：

1. **空格侧 48 次全部失败（0/48）**，下划线侧 36/48 成功 → 空格是脏数据，
   替换为下划线是唯一正确解（`img`/`www` 连 `/static/` 本身都 404，
   只有根路径 200 —— 它们是 Web/API 主机，压根不服图片）。
2. **`img` 和 `www` 一直躺在候选池里，是本项目"一直被报成 404"的直接来源。**

危害不是"多失败两次"这么简单：

- 它们 DNS 能解析、TCP 能连上、还会返回**真实的 HTTP 响应**，
  于是 `ImageHostHealth` 那套"只隔离连接层失败"的机制**永远不会隔离它们**；
  每次换源遍历都要为它们各付出一发，在预算有限的串行兜底里把可用源挤到队尾；
- 它们返回的 **404** 会顶掉合法存储节点给出的 **403**，让界面把"路径写错"
  报成"图片不存在"——**一个方向完全相反的结论**，直接误导排查。

这两个域名已从 `ImageHosts` 移除，并新增 `ImageHostsTest` 把池子钉死为
"逐个实测过 `/static/<真实图>`、`/static/`、根路径三类地址"的 6 个域名。

单元测试 **395 项全绿**（新增 `SuspiciousPathCharsTest` 8 项、`ImageHostsTest` 5 项，
含"可打印 ASCII 全谱都不该被判为可疑"与"已知不服图片的域名不许再进池"两条反向保护）。

### v1.11.32 修复说明：按 Unicode 类别一刀切 + 拦截器兜底

**v1.11.31 仍然是"枚举"的思路** —— 列了几个已知的空白字符去替换。枚举永远在
追着补：用户随后又报了同一类错误，说明那个位置上的字符**不在当时列的名单里**。

这次不再猜字符，改成**按 Unicode 类别判定**。只要字符属于这五类，一律视为
"路径里的不可见垃圾"并还原为下划线：

| 类别 | 代号 | 包含 |
|---|---|---|
| 控制字符 | Cc | `\t \n \r`、U+000B、U+001C–U+001F、U+007F–U+009F |
| 格式字符 | Cf | 零宽 U+200B/200C/200D/200E/200F、U+2060、U+FEFF、U+180E、U+00AD |
| 空格分隔符 | Zs | U+0020、U+00A0、U+2000–U+200A、U+202F、U+205F、U+3000 |
| 行分隔符 | Zl | U+2028 |
| 段分隔符 | Zp | U+2029 |

为什么"取两个常用判据的并集"也不够 —— 它们**互有盲区**，而且都漏掉整个 Cf 类别：

| 判据 | 盲区 |
|---|---|
| `Char.isWhitespace()` | 漏 U+00A0（NBSP）、U+202F |
| `Character.isSpaceChar()` | 漏 U+2028/U+2029，漏所有 Cf |
| 两者并集 | 仍漏 U+200B、U+FEFF、U+180E 等全部零宽字符 |

这五类正是"屏幕上不占可见宽度、却在 URL 里真实存在"的全部来源，一次覆盖，
不存在"又发现一种"。可打印字符（含 CJK、`%`、`~`）一律保留，不会误伤合法路径。

**顺带堵掉一个真实漏洞**：`Media.safeImageUrl` 只修好了"从 API 响应拼 URL"
这一条路径，而取图片地址的调用点不止一处 —— 封面、头像、通知列表走的是
刻意保留原样的 `originalImageUrl`。任何一处漏掉，现象就退化成"章节图正常、
封面固定加载失败"，用户看到的依旧是"图片不存在"，而日志里那个 URL
**看起来完全正常**。

现在在 Coil 拦截器链**最外层**加了一道守卫（`ImagePathGuardInterceptor`），
放在节流与换源之前：

- 只要最终请求的是 `/static/` 图片，进网络前路径一定被治过，**不依赖调用方自觉**；
- 按 `pathSegments`（已解码）逐段处理再用 `addPathSegment` 重新编码，
  所以 `%20`、`%C2%A0` 这类**已经是编码态**的脏值也会被认出来，不会漏网；
- 放在最外层还有个实际好处：日志打在链路入口，后续所有层看到的都是修好的
  URL —— 不会再出现"日志里明明是干净地址、却依然 404"这种自相矛盾的现场。

只改路径不改域名：各镜像是同一份存储的入口，`/static/{path}` 在哪个域名下都
指向同一张图。换域名是另一层（`PreferredHostInterceptor` / 降级竞速）的职责
—— **地址本身写错了，换多少个源都没用**。

用户报的三条地址实测复核（`storage-b`，6 个边缘 IP 交叉验证，结论完全一致）：

| 用户报告 | 原样形态（含脏字符） | 归一化后 |
|---|---|---|
| 第13页 `7f8b7261…` | 6/6 全部 **403** | 6/6 全部 **200** |
| 第12页 `6a7c17f1…` | 6/6 全部 **403** | 6/6 全部 **200** |
| 第72页 `1bd3dbc9…` | 6/6 全部 **403** | 6/6 全部 **200**，626131 字节真实 JPEG |

403 响应体固定 178 字节，是 nginx 自带的 `403 Forbidden` 页 —— 说明**该目录在
源站根本不存在**，不是权限问题、不是限流、不是源站不稳定，就是路径写错了。

单元测试 382 项全部通过（新增 `ImagePathSanitizerTest` 10 项、扩充
`MediaUrlTest` 到 29 项），其中包含"整个五类不可见字符全谱"的参数化断言，
以及"可打印字符一律保留不被误伤"的反向保护。

### v1.11.31 修复说明：空白字符全谱覆盖 + 下载链路对齐

**v1.11.30 的修复有个盲区**：只写了 `.replace(" ", "_")`，只能命中**普通空格**
（U+0020）。而 `\u00A0`（不间断空格）在 Java 的 `Character.isWhitespace()` 里
返回 **false**，却渲染得和普通空格**一模一样** —— 这种脏值会让修复**静默失效**，
现象与完全没修一致，极易被误判成"修复没生效"。

实测（同一张图、同一目录段，4 个边缘 IP 交叉验证，结论一致）：

| 目录段 | 状态 |
|---|---|
| `sub_storage` + U+0020 普通空格 + `1` | 403 |
| `sub_storage` + U+00A0 不间断空格 + `1` | 403 |
| `sub_storage` + U+3000 全角空格 + `1` | 403 |
| `sub_storage` + U+0009 制表符 + `1` | 403 |
| `sub_storage_1`（下划线） | **200** |

所有空白变体都取不到图，只有下划线是正确字符 —— 所以统一按字符集归一化是
安全的，不存在误伤合法路径的风险。另加了一条"归一化后 URL 中不残留任何空白
字符"的回归断言，防止以后再出现半个修复。

**同时修掉一处不一致**：离线下载走的是 `originalImageUrl`（**不做任何归一化**），
而在线阅读走 `safeImageUrl`（已归一化）。同一条路径两边行为不同，会导致
**"能看不能下"**这种极难排查的现象。现在下载改用新增的 `normalizedImageUrl`
—— 与 `safeImageUrl` 相同的归一化，但**永不返回 null**：下载的语义是"尽力去抓"，
静默丢弃会让分页循环把"这一页全畸形"误判成"没有更多页"而提前终止，
反而丢掉后面本来正常的页。

### v1.11.30 修复说明：路径里的空格 → 下划线

**现象**：某几页报 `图片不存在（HTTP 404）`，`url` 里出现形如
`/static/tobs/sub_storage 1/7f/8b/xxx.jpg` 的地址 —— 目录段 `sub_storage 1`
中间是一个**真正的空格**。

**这不是复制粘贴的问题。** 报错界面那一行是逐字打印 App 内存里的 URL
（`ComicItem.kt` 里 `append("\nurl: ${page.url.take(200)}")`，无任何美化），
而该 URL 由服务端返回的 `path` 字段直接拼接而来。空格存在于**服务端数据**里。

**为什么必然取不到图**：`sub_storage 1` 里的空格被 OkHttp 编码成 `%20` 发出去，
请求"看起来完全正常"，链路上没有任何一层会拦它。但源站的真实目录名是下划线。
实测（`storage-b`，4 个边缘 IP 交叉验证，结论完全一致）：

| 路径段 | 状态 | 字节数 |
|---|---|---|
| `sub_storage%201`（空格） | 403 | 178 |
| `sub_storage_1`（下划线） | **200** | **128093** |

403 响应体是 nginx 自带的 `403 Forbidden` 页（`nginx/1.10.0 (Ubuntu)`），
说明该目录在源站**不存在** —— 不是权限问题，是路径写错了。

**修复**：在 URL 拼接处（`Media.buildStaticUrl`）把路径段内的空格还原为下划线。
这是唯一知道"这是路径、不是用户输入"的地方，且在 OkHttp 之前修好，
选源/重试/缓存各层才能看到同一个正确 URL（`diskCacheKey` 也随之稳定）。

### v1.11.29 修复说明：`storage-b` 图片失败（HTTP 404）

服务端会把 `/static/tobs/xxx.jpg` 在任意域名下 `301` 重定向到
`storage-b.picacomic.com/static/xxx.jpg`。而 `storage-b` 的可用性**按 IP 分裂**：

| IP | `storage1` | `storage-b` |
|---|---|---|
| `104.16.253.195` | 200 | **200** |
| `104.17.227.96` | 200 | **200** |
| `104.20.33.201` | 200 | 403 |
| `104.21.20.188`（原出厂默认） | 200 | 403 |

OkHttp 对 IP 列表**只在连接失败时**才换下一个，**403 不触发切换**。由于每次
解析返回顺序相同，列表首位一旦是"对 `storage-b` 403"的 IP，图片就**确定性失败
且重试无效**。修复：兜底池只收录双 200 的 IP，并在 DNS 层做 IP 轮转。
